# Windows 麻将观察 Agent 设计方案

> 状态：Draft v0.1  
> 首个规则集：武汉红中赖子杠  
> 首个平台形态：Windows 桌面端，监控用户选择的任意麻将窗口  
> 首个视觉方案：多模态模型主识别，结构化牌局状态作为唯一权威记忆

Agent 编排、长期记忆、混合检索、自学习边界和 .NET 模块落位的实现级设计，见 [Agent 与长期记忆后端设计方案](backend-agent-memory.md)。

## 1. 项目摘要

本项目是一个 Windows 桌面麻将观察 Agent。用户选择一个麻将游戏窗口后，系统持续观察牌面变化，将视觉结果转换为结构化牌局事件，维护完整的本局状态，并在轮到用户决策时提供胡牌、牌效、攻守、危险度和规则提示。

Demo 不绑定某个具体微信小程序。不同游戏的颜色、布局、牌面皮肤和癞子位置由多模态模型首次理解，并保存为可复用、可版本化的窗口视觉档案。后续牌局优先加载已有档案，不再从零理解界面。

系统不读取游戏进程内存、不注入游戏、不拦截内部协议、不自动点击或出牌。核心定位是允许场景下的观察、训练与决策提示，具体在线平台的使用仍需遵守其服务条款。

## 2. 核心设计结论

1. Agent 平时处理结构化文字状态，不持续直接观看完整画面。
2. 多模态模型是 Demo 的主要视觉解析器，但只是感知模块，不是牌局事实来源。
3. 所有视觉结论必须经过时序、牌数和规则校验，才能写入正式牌局状态。
4. 每个游戏界面拥有持久化的窗口、布局、皮肤和规则档案。
5. 当前牌局采用事件溯源：事件日志是事实来源，`GameState` 是可重建的状态快照。
6. 胡牌、合法动作、牌效和番数尽量由确定性规则与计算引擎完成，不交给大模型猜测。
7. Agent 需要长期适应，但不能在未经验证的情况下自主修改规则和策略。

### 2.1 产品界面层级

产品由两个同时存在但职责不同的界面构成：

**主窗口仪表盘**是程序控制中心，负责配置、运维、诊断、窗口档案、规则、隐私、历史牌局和局内完整可视化。它允许用户深入检查系统如何理解牌局，但不是每巡操作入口。

**悬浮助手**是牌局中的核心功能，负责在不抢焦点、不遮挡操作区的前提下主动显示推荐牌、风险、置信度和简洁理由。系统在后台持续观察和计算，用户无需手动录入牌面，也不需要先打开主窗口才能获得建议。

两种界面读取同一份 `GameState` 和 `DecisionSnapshot`：

```text
                         ┌─ 主窗口仪表盘：完整状态、配置、运维、诊断
GameState + Decision ────┤
                         └─ 悬浮助手：结论优先、低干扰、即时建议
```

主窗口关闭到托盘后，捕获、识别、状态更新、策略计算和悬浮提示仍可继续运行。

对手回合期间，Agent 仍然持续更新牌型倾向、可能听牌状态、危险度和下家吃牌风险。普通变化只更新低干扰信息条；用户回合、明显攻守转换、承包风险或高危险变化才触发主动展开。所有对手意图都属于基于公开信息的推测，不能作为确定事实展示。

## 3. “长期学习”的定义与边界

牌局理解确实是一个持续过程，但这里包含三种不同层次的学习。

### 3.1 本局持续理解：必须具备

这是 Agent 的工作记忆，不是模型训练。

系统需要随着每次摸牌、出牌、吃碰杠和规则提示持续更新对本局的理解：

- 自家手牌及刚摸入的牌；
- 四家弃牌河和副露；
- 当前癞子、皮、红中杠状态；
- 已出现牌数量；
- 当前玩家、巡目和牌局阶段；
- 开口次数、翻数和承包关系；
- 不确定观察及其候选解释；
- Agent 历史建议及当时依据。

这一层必须实时、确定、可回滚。它通过 `GameEvent + GameState` 实现，不依赖大模型上下文记忆。

### 3.2 跨窗口视觉适应：Demo 就应具备

这是真正需要长期持久化的能力。系统应记住：

- 某个窗口的麻将桌布局；
- 手牌、弃牌、副露、癞子和提示区域；
- 当前皮肤下每类麻将牌的视觉外观；
- 横置牌、选中牌、灰暗牌和动画状态；
- 该窗口曾经使用的规则配置；
- 用户纠正过的识别错误；
- 界面更新前后的档案版本。

这种学习本质上是更新 `WindowProfile` 和视觉样本，不是重新训练大模型。

### 3.3 跨牌局策略学习：后期可选

策略学习可以从大量已验证牌局中改进危险度、对手倾向和出牌收益估计，但不应进入首个 Demo 的核心路径。

首版策略应优先采用：

- 武汉麻将规则引擎；
- 合法胡牌与牌型枚举；
- 癞子替代计算；
- 有效进张和牌效排序；
- 可解释的启发式攻守规则；
- 后期再加入蒙特卡洛模拟。

跨牌局机器学习必须采用离线训练、固定测试集、版本发布和回滚流程，不能让生产中的 Agent 根据单局输赢直接修改策略。单局结果噪声很大，用户也可能没有执行 Agent 建议，直接在线强化容易产生错误归因。

### 3.4 不允许自主学习的内容

以下内容只能通过验证后的配置或版本更新修改：

- 麻将基本规则；
- 胡牌合法性；
- 特殊牌映射；
- 计分公式；
- 数据保留和隐私策略；
- 外部 API 权限；
- 自动操作边界。

一句话概括：**Agent 应当持续记忆和适应，但不能无监督地改写自己的规则和决策标准。**

## 5. 核心组件

### 5.1 Desktop Shell

职责：

- 枚举并选择 Windows 窗口；
- 使用 Windows Graphics Capture 获取窗口画面；
- 管理窗口移动、缩放、最小化和 DPI 变化；
- 显示置顶、透明、鼠标穿透的提示层；
- 提供暂停监控、隐私设置、纠错和复盘入口。

Desktop Shell 内部进一步拆分：

- `ControlCenterWindow`：配置与运维仪表盘；
- `OverlayWindow`：牌局核心悬浮助手；
- `TrayHost`：后台常驻、快速状态和退出入口；
- `CalibrationWindow`：首次标定与手动纠正；
- `ReplayWindow`：牌局复盘。

主窗口可以展示完整牌局状态、事件流、API 延迟、识别置信度和档案信息；悬浮助手只展示当前最重要的决策信息。

### 5.2 Change Detector

这是轻量本地模块，不识别麻将内容，只判断画面是否值得重新处理。

- 对关键区域计算像素差异或感知哈希；
- 动画期间等待画面稳定；
- 只有牌面明显变化时才触发多模态请求；
- 对重复帧去重；
- 控制 API 调用频率。

### 5.3 Multimodal Perception Provider

封装具体多模态 API，支持替换提供商。模型必须按固定 JSON Schema 返回结果。

三种工作模式：

1. `calibrate`：首次完整理解陌生窗口并创建档案；
2. `observe`：加载档案，只分析发生变化的区域；
3. `recover`：状态矛盾或界面漂移时重新理解完整牌桌。

模型输出的是 `Observation`，不能直接写入 `GameState`。

### 5.4 Profile Manager

管理长期窗口记忆：

- 识别当前窗口对应哪个既有档案；
- 保存布局、皮肤、视觉锚点和规则偏好；
- 管理候选、确认和拒绝的视觉样本；
- 记录档案版本并支持回滚；
- 检测界面更新和布局漂移。

### 5.5 Observation Resolver

将多模态模型的候选观察转换为可信事件：

- 多帧一致性校验；
- 手牌和副露数量校验；
- 同一实体牌最多四张校验；
- 玩家动作时序校验；
- 武汉麻将特殊牌规则校验；
- 与上一个 `GameState` 做差异推断；
- 冲突时保留多个候选，不强行猜测。

### 5.6 Event Store 与 Game State

采用事件溯源：

- `GameEvent` 是正式事实；
- `GameState` 由事件序列归并得到；
- 定期保存状态快照，加速恢复；
- 纠错使用补偿事件，不直接删除历史；
- 程序重启后可恢复未结束牌局。

### 5.7 Rule Engine

首个规则族为武汉红中赖子杠，支持组合式变体：

- 经典红中赖子杠；
- 开口翻；
- 口口翻；
- 七皮四癞；
- 后续红中发财杠等变体。

规则模块拆分：

```text
TileSetRule
IndicatorRule
ActionRule
WinShapeRule
OpenRequirement
FanRule
LiabilityRule
SettlementRule
```

当前参考资料：

- [百度百科：红中赖子杠](https://baike.baidu.com/item/%E7%BA%A2%E4%B8%AD%E8%B5%96%E5%AD%90%E6%9D%A0/1810660)
- [知乎：武汉麻将初学者入门——七皮四癞红中癞子杠口口翻](https://zhuanlan.zhihu.com/p/537567818)

两份资料存在玩法差异和个别内部矛盾，因此所有未经过目标平台验证的规则都应标记来源和验证状态。

### 5.8 Strategy Engine

职责：

- 枚举合法出牌；
- 计算胡牌距离和有效牌；
- 处理癞子、皮和二五八将约束；
- 比较小胡和大胡发展路线；
- 估计可见牌剩余数量；
- 评估开口、杠牌和承包风险；
- 输出候选动作、评分和可解释特征。

策略引擎输出计算结果，Agent 将其转成简短、自然的提示。

### 5.9 Knowledge Store

长期攻略库应包含：

- 规则说明；
- 术语；
- 牌型案例；
- 攻守原则；
- 常见错误；
- 来源、适用规则和可信度。

知识库用于解释与检索，不替代合法性和牌效计算。

## 6. 记忆模型

### 6.1 瞬时视觉记忆

- 最近数秒帧环形缓冲区；
- 默认不落盘、不上传完整窗口；
- 用于多帧确认和异常恢复；
- 到期立即释放。

### 6.2 WindowProfile 长期记忆

```json
{
  "profile_id": "wechat-wuhan-a",
  "identity": {
    "process_name": "WeChat.exe",
    "window_class": "Chrome_WidgetWin_0",
    "title_patterns": ["微信", "小程序"],
    "aspect_ratio": 1.7778,
    "visual_fingerprint": "phash:..."

  "layout_profile": "layout-v3",
  "skin_profile": "ivory-green-v1",
  "rule_profile": "seven-skin-four-laizi-koukoufan",
```

不能使用临时窗口句柄作为唯一身份。匹配应综合进程、窗口类、标题模式、比例、视觉锚点和用户命名。

### 6.5 策略与用户适应记忆

后期可记录匿名化、可删除的用户偏好：

- 用户更偏好稳健还是激进提示；
- 用户是否经常忽略某类风险；
- 哪类解释最有帮助；
- 用户是否执行了建议。

这类记忆只影响提示方式和候选排序权重，不能修改麻将规则。

## 7. Agent 工作循环

```text
选择窗口
  → 匹配 WindowProfile
  → 未匹配时执行 calibrate
  → 加载或创建 GameSession
  → 本地变化检测
  → 多模态 observe
  → Observation Resolver 校验
  → 追加 GameEvent
  → 更新 GameState
  → 判断是否需要决策
  → Strategy Engine 计算
  → Agent 检索规则与攻略
  → 输出悬浮提示
```

Agent 只在以下情况触发：

- 轮到用户操作；
- 癞子、皮或规则被揭示；
- 有人吃碰杠导致局面变化；
- 进入高风险或海底阶段；
- 状态出现矛盾；
- 用户主动提问。

## 9. 长期学习管线

```text
多模态观察
  → 候选视觉记忆
  → 多帧/规则/用户验证
  → WindowProfile 正式更新
  → 形成匿名训练样本（用户可选）
  → 离线训练或评估
  → 新版本影子测试
  → 达标后发布
  → 支持回滚
```

所有学习数据都需要记录：

- 来源；
- 所属窗口档案；
- 规则版本；
- 模型版本；
- 置信度；
- 是否由用户确认；
- 是否允许用于训练。

## 10. 防止记忆污染

视觉档案条目采用三态管理：

```text
candidate   模型刚发现，尚未确认
confirmed   已通过规则、多帧或用户验证
rejected    已证明错误
```

长期档案只接收 `confirmed` 数据。其他保护措施：

- 新档案版本不可覆盖旧版本；
- 低置信度观察不自动学习；
- 规则矛盾时优先暂停提示；
- 用户纠错生成补偿事件；
- 新策略先运行影子评估；
- 用固定牌局集做回归测试；
- 支持按档案或模型版本回滚。

## 11. 多模态请求上下文

日常观察不应反复发送全部历史。请求只包含：

- 当前发生变化的局部画面；
- 当前 `WindowProfile` 摘要；
- 上一份确认的 `GameState` 摘要；
- 最近若干关键事件；
- 固定 JSON 输出 Schema。

只有首次标定、布局漂移或状态恢复时发送完整牌桌画面。

## 12. 本地持久化

Demo 推荐：

- SQLite：档案元数据、版本、事件、状态快照、建议和纠错；
- 本地文件：裁剪后的视觉锚点和麻将牌参考样本；
- JSON：模块协议和可导入导出的规则配置；
- Windows Credential Manager：API Key；
- 内存环形缓冲：短期截图。

建议数据表：

```text
window_profiles
layout_profiles
skin_profiles
rule_profiles
visual_exemplars
profile_versions
game_sessions
game_events
state_snapshots
observations
agent_decisions
user_corrections
knowledge_entries
```

## 13. 隐私与安全

- 默认只捕获用户明确选择的窗口；
- 默认不保存完整窗口截图；
- 保存视觉样本时优先只裁剪麻将区域；
- API 请求前遮罩头像、昵称、聊天和其他非牌局内容；
- 训练数据贡献必须单独开启；
- 支持查看和删除每个窗口档案及历史牌局；
- API Key 不写入配置文件或日志；
- 所有 Agent 状态写入均保留审计记录。

## 14. Demo 技术建议

首版以 Windows 能力和交付速度为优先：

- 桌面端：.NET 8 + WPF；
- 窗口捕获：Windows Graphics Capture；
- 数据库：SQLite；
- 多模态接口：Provider 抽象 + JSON Schema；
- 规则与状态核心：C# 强类型模块；
- 后续训练和数据处理：Python 工具链；
- 提示层：透明置顶、鼠标穿透窗口。

如果未来确定需要跨平台，可以保留核心协议，将 Desktop Shell 替换为其他 UI 技术；Demo 不应为了潜在跨平台牺牲 Windows 捕获和悬浮层的稳定性。

- 多模态按变化区域输出 Observation JSON；
- GameEvent 和 GameState；
- 武汉红中赖子杠基础规则；
- 自家手牌、癞子、皮、摸牌和出牌识别；
- 基础胡牌与推荐出牌；
- 悬浮提示；
- 用户纠错；
- 牌局事件回放。

### 可以延后

- 完整四家危险度模型；
- 个体对手长期画像；
- 自动训练本地视觉模型；
- 蒙特卡洛策略；
- 多平台支持；
- 自动点击和出牌；
- 未经验证的复杂计分变体。

## 16. 评估指标

### 感知

- 自家手牌识别准确率；
- 摸牌、出牌、吃碰杠事件准确率；
- 窗口档案匹配准确率；
- 首次标定后复用成功率；
- 每局需要完整重新标定的次数。

### 状态

- 牌数守恒错误率；
- 从事件重放得到相同状态的比例；
- 异常后自动恢复成功率；
- 用户每局需要纠错的次数。

### 决策

- 合法建议率必须为 100%；
- 胡牌和听牌判断准确率；
- 推荐动作计算延迟；
- 建议解释与计算结果一致率。

### 性能与成本

- 从稳定画面到提示的延迟；
- 每局多模态 API 调用次数；
- 每局 API 成本；
- CPU、内存和网络使用；
- 重复帧过滤率。

## 17. 主要风险

| 风险 | 应对 |
|---|---|
| 多模态模型漏牌或数错 | 时序校验、牌数守恒、用户纠错 |
| 不同平台规则不一致 | 组合式 RuleProfile，记录来源和验证状态 |
| 档案匹配到错误窗口 | 多特征匹配，低置信度时要求确认 |
| UI 更新污染旧档案 | 档案版本、漂移检测和回滚 |
| API 延迟影响提示 | 变化检测、区域裁剪、并行本地策略计算 |
| 调用成本过高 | 档案复用、去重、只分析关键事件 |
| Agent 自主学习错误策略 | 离线学习、固定评测、影子测试、人工发布 |
| 隐私泄漏 | 本地裁剪、遮罩、最小上传和可删除数据 |

## 18. 建议实施阶段

### Phase 0：协议与模拟器

- 定义牌编码、Observation、GameEvent 和 GameState；
- 实现事件回放；
- 用手工 JSON 模拟完整牌局；
- 验证武汉麻将基础规则。

### Phase 1：多模态视觉 Demo

- Windows 窗口选择与捕获；
- 首次标定；
- WindowProfile 持久化；
- 手牌和关键事件识别；
- 用户纠错。

### Phase 2：决策 Agent

- 牌效与胡牌计算；
- 规则和攻略检索；
- 悬浮提示；
- 牌局复盘。

### Phase 3：稳定性与成本优化

- 更精细的变化检测；
- 视觉档案复用；
- 多模态异常恢复；
- 收集经授权的视觉样本；
- 评估本地专用视觉模型。

### Phase 4：策略学习

- 建立离线牌局数据集；
- 危险度和对手倾向模型；
- 蒙特卡洛或学习型局面评分；
- 影子评估和版本化发布。

## 19. 尚待确认的产品决策

1. Demo 使用哪一个多模态 API 和模型；
2. 用户是否接受本地保存裁剪后的视觉样本；
3. 首个目标小程序采用开口翻还是口口翻；
4. 是否包含七皮四癞；
5. 提示形式是悬浮牌标记、侧边栏还是两者兼有；
6. 首版是否只分析自家手牌，还是同时识别四家弃牌和副露；
7. 历史牌局默认保存多久；
8. 开源许可证和模型/数据许可证选择。

## 20. 最终判断

Agent 需要长期学习，但首版最重要的不是让模型“越打越会出牌”，而是让系统：

1. 在一局之内持续形成正确理解；
2. 下一次看到相同窗口时记得如何观察；
3. 从经过验证的用户纠错中改进视觉档案；
4. 始终保持规则、状态和策略可解释、可测试、可回滚。

完成这些基础后，跨牌局策略学习才有可信的数据和评估条件。
